# 能力條目指南 — 多年期技術路線圖 (Multi-Year Technical Roadmap)

`對應 JD 條目`: Experience defining and delivering multi-year technical roadmaps that balance
short-term execution with long-term architectural integrity across multiple engineering teams.

`為什麼需要這份指南`: [Meta Principal 檔](../../jd/meta/software_engineer_principal.xf_apac_products.md)
的缺口分析指出, [Resume.md](../../Resume.md) 目前`全部以專案與框架為單位`陳述,
沒有任何一段是以`年`為時間軸的路線圖敘事. 事證存在, 缺的是`敘事框架`.

## 1. 這條要求實際在問什麼 (Signal Decode)

一句話裡藏了四個獨立訊號, 面試官會分開驗證, 只答其中一個會被判定為`只有專案經驗`:

| 訊號 | 面試官要聽到的證據 | 常見失分 |
| --- | --- | --- |
| `Defining` | 你決定了`做什麼與不做什麼`, 有排序準則與被你砍掉的項目 | 只說接到需求後怎麼做 |
| `Multi-year` | 一條`跨年份`的主軸, 且第 N 階段`因為`第 N-1 階段才做得成 | 講成數個互不相干的專案 |
| `Balance` | 至少一次你`刻意選了短期解`, 以及你如何把債還掉 | 只講理想架構, 沒有妥協 |
| `Across multiple teams` | 別的團隊`採用`了你的東西, 而你不是他們的主管 | 只講自己團隊內的協作 |

`Balance` 最容易被追問. 只講長期會被讀成`不懂交付`, 只講短期會被讀成`沒有架構觀`.
必須自己主動提出一次`我當時選了醜的做法`並說明還債時點.

## 2. 主敘事 — 錢包資料合規六階段 (ByteDance 2023/01 ~ 2026/08)

這條線`本身就是合格的多年期路線圖`, 因為七個階段是`能力階梯`而非並列專案:
每一階都要用到前一階的產出, 抽掉任何一階, 後面全部做不成.

`一句話主軸`: 讓`資料落在哪裡`從一次性的搬遷專案, 變成平台可設定的屬性.

`記憶口訣`: 落得下去 → 搬得過去 → 隨時可換 → 管得住一生 → 別人能用 → 搬得更省 → 掛了還在.

```mermaid
flowchart LR
    S0["0 新資料中心落地<br/>內外部服務對齊"] -->|"區域可承載資料"| S1["1 EU 資料遷移<br/>法遵期限驅動"]
    S1 -->|"遷移能力就位"| S2["2 全球換區合規<br/>最終合規一致性"]
    S2 -->|"合規需求由專案上升為制度"| S3["3 資料 SDLC"]
    S3 -->|"生命週期規則可被流程承載"| S4["4 高階流程抽象化"]
    S4 -->|"抽象暴露底層瓶頸"| S5["5 資料通道最佳化"]
    S5 -->|"通道穩定後才談備援"| S6["6 交易資料備援"]
    S4 -->|"其他業務線接入"| ORG["跨部門採用"]
```

| 階段 | 能力躍遷 | 在敘事中的角色 |
| --- | --- | --- |
| `0 新資料中心落地` | 把內部與外部服務對齊到新資料中心, 跨團隊協調 | `Across teams` 的起點, 說明後續每一階都站在這個基礎上 |
| `1 EU 資料遷移` | 法遵日期驅動的區域落地 | 建立`外部強制期限`, 說明第 1 年幾乎沒有架構餘裕 |
| `2 全球換區合規` | 從一次性遷移變成`用戶隨時可換區`, 以最終合規一致性收斂 | 粒度與可回滾性的躍遷 |
| `3 資料 SDLC` | 合規從`每個專案自己檢查`變成`資料生命週期的屬性` | 從執行者升級為`規則制定者`的轉折點 |
| `4 高階流程抽象化` | 從錢包專用流程變成`任何業務線可接` | `Across teams` 訊號的主證據 |
| `5 資料通道最佳化` | 收斂第 1 階段留下的一次性通道 | `Balance` 訊號的主證據, 見第 3 節 |
| `6 交易資料備援` | 從遷移能力反轉為`容錯能力` | 量化收尾: 實作與維護成本降低 `2 個職等` |

`需你補上的時間軸`: 七階段對應 3 年 8 個月, 講述時每階段要能說出`大約哪一年`.
建議自行確認後標註, 面試官問到年份接不上會直接折損 `Multi-year` 訊號.

## 3. 這條線最值錢的地方 — 階段 5 就是還債

`資料通道最佳化`這幾個字是整條敘事裡最強的一段, 但很容易被自己輕描淡寫帶過.

它的意思是: 第 1 階段為了趕法遵期限, 每個服務各自接了自己的搬遷通道, 這是`刻意的短期解`;
第 5 階段把這些通道收斂成一套跨資料中心傳輸, 這是`把債還掉`.
而第 2 階段的全球換區早已把粒度從服務降到用戶, 讓遷移從`停機式的大搬家`
變成`可漸進, 可回滾的單用戶操作`, 這是還債之前先降低風險.

面試時務必用這個順序講: `先承認第 1 年幾乎全是短期解` → `說明當時為什麼那是對的決定` →
`用第 5 階段證明債確實還掉了`.
主動承認妥協會建立可信度, 這比宣稱自己一開始就設計得完美有效得多.

## 4. 短期與長期怎麼平衡 (可宣稱的機制)

問 `how do you balance` 要給`機制`而不是`態度`. 你實際做過, 只是沒命名:

- `以外部期限倒推`: 法遵日期不可談判, 路線圖從合規日往回排, 架構投資只能塞進期限之間的縫隙.
- `先接線, 後抽象`: 前幾個案子容許重複與醜解, 但每次都記錄形狀; 到第 N 個才收斂成介面.
  沒有 N 個樣本就抽象, 抽象一定是錯的 - 階段 1 到 5 就是這個原則的實例.
- `廢止日期視為交付項`: 短期解進入路線圖時同時寫下移除日期, 讓債務有到期日而非無限展期.
- `粒度換取可回滾性`: 把操作單位縮小 (服務 → 用戶) 是降低風險最便宜的手段, 優先於加測試.
- `以職等衡量維護成本`: 用`需要幾個什麼職等的人才維持得住`表達長期成本, 比講技術債更容易讓管理層買單.
- `框架的採用是自願的`: 跨部門推廣沒有職權槓桿, 只能靠`接入比自建便宜`, 因此第一版必須極度好接.

## 5. 一致性與備援的深挖題準備 (Highest Risk)

錢包 + 跨資料中心 + 一致性, 這組合會讓有支付背景的面試官 (Airwallex, Stripe, OKX 這幾檔)
直接往底層鑽. 以下請先備好答案, 答不出來會連帶折損整條敘事的可信度:

- 遷移進行中, 同一個用戶的餘額讀寫落在哪一邊? 切換的臨界點怎麼定義?
- 寫入雙寫 (dual-write) 還是走變更資料捕捉 (CDC, Change Data Capture)? 為什麼?
- 冪等性 (idempotency) 怎麼保證? 重送與重放怎麼區分?
- 對帳 (reconciliation) 機制長什麼樣? 發現不一致時是自動修復還是人工介入?
- 回滾策略是什麼? 已經搬過去的用戶要退回來, 資金狀態怎麼處理?
- 一致性等級的取捨: 哪些欄位接受最終一致 (eventual consistency), 哪些必須強一致?

`守則`: 講`機制的形狀`, 不講內部系統名稱, 實際流量數字或與監理機關往來的細節.
用`一個受法規約束的錢包業務`這種抽象描述即可, 面試官要的是設計推理, 不是內部資料.

## 6. 面試回答骨架 (三種問法)

`問法 A - 講一個你定義的多年期路線圖`
六階段各 15 秒, 以`能力階梯`串接, 最後 15 秒講 2 個職等的量化結果. 全長 2 分鐘內.

`問法 B - 你怎麼在期限壓力下維持架構完整性`
直接用第 3 節的三段式: 承認短期解 → 說明當時為何合理 → 用階段 5 證明還債.

`問法 C - 你怎麼讓別的團隊照你的路線圖走`
用階段 4 的高階流程抽象化: 你沒有他們的管理權, 唯一槓桿是接入成本低於自建成本.
可補 Change Healthcare 的共用框架 (EventBus, Secret Manager plugin) 作為第二個樣本,
證明這不是單次僥倖.

## 7. 履歷改寫方向 (Resume.md)

## 8. 誠實邊界 (Do Not Claim)

- 不要宣稱`擁有組織級路線圖`. 你的層級是`一個技術領域跨數個團隊`, 講成 org-level 追問時會崩.
- 不要把 TSMC 的 5 個月講成多年期經驗, 它只能當`路線圖起手式`的補充例子.
- 不要宣稱管理過多個團隊. 直接帶人規模是 `5 人`, 跨團隊影響力來自`框架採用`而非匯報線,
  主動說出這個區分反而加分.
