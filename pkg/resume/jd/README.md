## 分數的意義 (Scoring Rubric)

分數是 `履歷 (Resume.md) 對 JD 硬性要求的覆蓋率`, 加上軟性要求與領域相鄰度的調整,
`不是` 錄取機率. 對照基準:

| 區間 | 意義 |
| --- | --- |
| `80 以上` | 硬性要求全數達標, 缺口僅在可自學的工具層, 應列為主投 |
| `65 - 79` | 硬性要求達標但有一項領域缺口 (支付, 會計, 加密貨幣等), 值得投, 需準備領域說法 |
| `50 - 64` | 有一項結構性缺口 (客戶面向經驗, 管理幅度), 屬拉伸型, 面試本身有情報價值 |
| `50 以下` | 缺口為職涯類型或核心語言等級, 不建議投遞, 保留作為門檻參照 |

## 台灣職缺的地點前提 (Taiwan Postings)

本庫預設以`新加坡`為工作地點, 因為履歷現況是新加坡 PR 且常駐新加坡.
`tsmc/` 底下 14 檔是唯一的例外, 工作地點全部在`台灣` (部分明列新竹廠區).

這批的評分`仍然只計算履歷對 JD 硬性要求的覆蓋率`, 不因地點折抵, 以維持與其他檔案的可比性.
但實際投遞前必須額外處理兩件事, 兩者都寫在各檔的 `我的對位敘事`:

- `搬遷`: 薪酬需以台灣計價, 且涉及放棄新加坡在地累積, 這是分數之外的獨立決策.
- `再任 (rehire)`: 履歷有 2022 年 3 月至 7 月在 TSMC 任職 5 個月的紀錄 (離職原因為文化契合度,
  主管與部門經理皆給予肯定). 這段一定會被內部系統標記, 應主動說明而非迴避.

## 同一份 JD 的多職級版本 (Duplicate Postings)

Airwallex 的 `Staff / Senior Software Engineer, Billing` 兩檔在 MyCareersFuture 上的
`職務描述本文完全相同 (byte-identical)`, 僅 `薪幅`, `最低年資` 與 `職缺數` 不同.
遇到這類雇主同時掛多職級的情況, 判準是 `投薪幅高的那一檔`:
既然硬性要求一字不差, 低薪版本不會提高錄取機率, 只會壓低起薪錨點.

Meta 的 `Forward Deployed Engineer, Enterprise AI` 兩檔則是另一種形態: `職缺標題字面完全相同`,
但內文分別自述為 `Senior` 與 `Staff`, 年資門檻 (6 年 vs 8 年) 與職責重心 (單案落地 vs 架構與路線圖) 都不同.
這類`非逐字相同`的多職級掛法, 兩檔都要獨立建檔並各自評分: 投遞仍以高職級那一檔為主,
但低職級版本要保留作為`降級 offer 的參照錨點`, 而不是直接視為重複.

Meta 的 `Business Support Engineer` 兩檔 (AdTech 與 Meta Business Agents) 是`同職級不同產品線`,
職責條目幾乎逐字相同, 差別在支援的產品與 AdTech 版多出的領域知識要求, 因此分開建檔但共用同一份缺口分析.

## 資料欄位 (Schema)

每份 JD 以 YAML front matter 作為`單一事實來源`, 排序總表由其產生, 不手工維護.

| 欄位 | 列舉值或格式 |
| --- | --- |
| `role_type` | `ic`, `staff_ic`, `architect`, `lead`, `manager`, `director`, `program_manager`, `pre_sales`, `strategy_lead` |
| `role_facing` | `internal`, `customer_facing` |
| `domain` | `payments`, `security`, `data_ai`, `ml_infra`, `low_latency_trading`, `cloud_platform`, `crypto`, `consulting_delivery`, `null` |
| `source` | `greenhouse`, `ashby`, `mycareersfuture`, `direct` |
| `education` | `master_cs`, `master`, `bachelor_cs`, `bachelor_stem`, `bachelor`, `null` |
| `status` | `not_applied`, `shortlisted`, `applied`, `screening`, `interviewing`, `offer`, `rejected`, `withdrawn`, `closed` |
| `min_years`, `score` | 整數, 未載明為 `null` |
| `posted`, `expiry`, `fetched`, `status_updated` | `YYYY-MM-DD`, 未載明為 `null` |
| `created` | `YYYY-MM-DD`, 建檔當天寫入且不再改動; 早於 3 個月且非投遞中者移入 `archive/<company>/` |

本文區塊固定為: `評估摘要` (blockquote) → `基本資訊` → `團隊背景` (選備) → `崗位職責` →
`任職要求` → `缺口分析` (選備) → `角色評估`, `機會`, `路線圖` (選備, 由 `job-analyze` skill 產出) → `我的對位敘事`.
`任職要求` 一律正規化為 `硬性要求 (Must-have)`, `加分要求 (Preferred)`, `其他條件 (Other)` 三塊,
各家 JD 的原始標題以 `— 原文` 保留.
